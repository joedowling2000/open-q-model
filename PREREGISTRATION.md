# Pre-registration — self-improvement on q/kdb+

**Written 2026-09-18, before any training run.** Every threshold, split and
decision rule below was fixed before the corresponding numbers existed.
Amendments are appended with a date and a reason, never edited away.

---

## The claim under test

> **Can a general-purpose open model teach itself q, using only its own output
> filtered by execution?**

Formally: does continued pretraining on permissively licensed human-written q,
followed by SFT on **q solutions generated by the base model itself and kept only
when they pass execution-based verification**, raise Q-HumanEval pass@1 from the
base model's score — and can it reach the q-specialised incumbent?

## Exam question, answerable with a number

> **Pass@1 of the trained model on Q-HumanEval (164 problems, current grader,
> one-shot, no tool use), compared with (a) its own base at 10.4% and
> (b) qqWen-32B-RL at 37.9%, both measured here under identical conditions.**

## Hypotheses

**H1 (self-improvement works).** The trained model beats its base by more than
the bootstrap CI on the difference. Verification-filtered self-generation adds
real capability, not just style.

**H2 (it closes the gap).** The trained model reaches or exceeds 38.4% — the
q-specialised model's score — without using any q-specialised model's output.

**H0 (it does not work).** No improvement beyond noise. The honest reading would
be that a 10% model cannot bootstrap q competence from its own samples, and that
qqWen's advantage comes from data we do not have (their RL stage, or the human
effort behind their problem set).

H0 is a real possible outcome and is worth reporting. A model that generates
correct q only 10% of the time may not produce enough correct samples to learn
from, and verification cannot create knowledge that was never sampled.

## Data lineage — the rule that defines this experiment

**Permitted in training:**
- Human-written q: our licence-filtered GitHub harvest (MIT/Apache/BSD/ISC/CC0),
  Kx documentation (CC-BY-4.0), `morganstanley/q_pretrained_dataset` (Apache-2.0
  — human-written code they harvested, not model output), `rd200/kdb_q`.
- q **generated by the base model itself** (`Qwen/Qwen3.5-27B`), kept only where
  execution verification passes.
- Problem *statements* from public sources, including the descriptions in
  `morganstanley/sft-python-q-problems`, used as generation seeds. **Disclosed.**

**Forbidden in training:**
- Any q produced by **qqWen** or any other q-specialised model. That is the
  comparison target; using its output would make H2 meaningless.
- Any output from frontier APIs whose terms forbid training competing models.
- Morgan Stanley's **q solutions** or **Python references** — both are model
  output from a different pipeline.
- Q-HumanEval, in any form.

If this rule is broken, the claim changes from "self-improvement" to
"distillation" and must be reported as such.

## Method, fixed in advance

1. **Continued pretraining.** LoRA on `Qwen/Qwen3.5-27B` over the permitted
   human-written corpus (~8M tokens after deduplication).
2. **Self-generation.** The base model writes problems (description, Python
   reference, input generator) and q solutions; solutions are kept only when they
   agree with the Python reference across ≥30 generated inputs, and only when
   those inputs are *discriminating* (see controls).
3. **SFT** on the surviving problem/solution pairs.
4. **Evaluation** at each stage under the protocol below.

RL is out of scope for this pre-registration. If it is added later, it gets its
own entry.

## Evaluation protocol, fixed in advance

- **Benchmark:** Q-HumanEval, 164 problems, KX harness, **current (post-PR-#7)
  grader**, grading code unmodified (our patches touch imports, concurrency and
  the q binary path only).
- **Mode:** one-shot, no tool use, no extended thinking (`--reasoning off`).
- **Sampling:** 30 samples per problem, temperature 0.8, max 512 tokens.
- **Quantisation:** Q8_0 for every model compared. One bf16 run on the final
  model, reported separately, to calibrate against leaderboard numbers.
- **Primary metric:** pass@1. Fixed now. Pass@5 and pass@10 are secondary and
  may not be substituted for pass@1 after seeing results.
- **Uncertainty:** bootstrap over the 164 problems, 10,000 resamples.

## Decision gates

| Gate | Threshold | If it fails |
|---|---|---|
| **A — pretraining sanity** | CPT checkpoint > base 10.2%, CI on the difference excludes zero | Report; diagnose before spending GPU on SFT |
| **B — self-improvement (H1)** | final model > base, CI on the difference excludes zero | H0; report it as a null result |
| **C — headline (H2)** | final pass@1 ≥ 38.4%, with the 95% CI lower bound above qqWen's point estimate | H1 without H2: "self-improvement works but does not close the gap" |

All three outcomes get written up. A null result here is informative: it would
say that bootstrapping a low-resource language from a weak model does not work,
which is worth knowing before anyone else spends a month on it.

## Controls that must run

1. **Contamination, both directions.** Every training record is checked for
   n-gram overlap against the 164 benchmark prompts *and* their reference
   solutions. Matches are removed and the count reported. The harvested GitHub
   corpus gets the same check — public q repos may contain HumanEval-style
   exercises.
2. **Discriminating inputs.** A generated problem is discarded unless its
   reference produces varied answers across the generated inputs (no single
   answer in >90% of cases). Without this, "always false" passes verification —
   it did, in our first pipeline run, for exactly this reason.
3. **Internal held-out split.** 15% of self-generated problems are never trained
   on and are scored separately, to detect a model that has learned our
   generation style rather than q.
4. **Base model re-measured, not quoted.** The 10.4% baseline is re-confirmed at
   30 samples under the same protocol as the trained model.
5. **Identical conditions.** Any comparison uses the same grader, quantisation,
   sample count and prompt protocol, or it is not reported as a comparison.
6. **Idiom check (descriptive).** Report the rate of `while`/`do` loops in
   generated solutions. Morgan Stanley's released q is full of imperative loops;
   if ours is too, the model has learned Python-in-q, which the benchmark score
   alone would not reveal.

## Threats to validity

- **Sampling floor.** A 10% model may not produce enough correct q for SFT to
  bite. Mitigation: many samples per problem; report the yield.
- **Verification is only as strong as the inputs.** Control 2 exists because our
  own pipeline initially accepted a known-wrong solution.
- **Self-generation narrows diversity.** Training on one model's output can
  collapse style. Control 3 and the idiom check watch for it.
- **Quantisation.** Everything is Q8_0; absolute numbers are not strictly
  comparable to bf16 leaderboard entries. Hence the single bf16 calibration run.
- **Small benchmark.** 164 problems; a 3-point difference is within noise. The
  CI rule in the gates exists for this reason.
- **Corpus concentration.** The top 10 repos are 62% of harvested bytes, so the
  pretraining corpus is not as diverse as its token count suggests.

## What gets published

The claim, the numbers, the data manifest (repo, path, licence, commit per file),
the scripts, the filter statistics, and the failures — including that our own
verification pipeline accepted a wrong solution until the discriminating-input
check was added.
